# 维护与发布

## 作者与分发

`atou42/cohub-skill` 是唯一主仓库：根 `skills/cohub` 与 `zh-CN/skills/cohub` 维护通用能力；`plugin/` 保存导入历史后的插件源码与可选交互。原 `atou42/cohub-plugin` 保留旧地址和升级桥接，不继续维护另一份 Skill。个人共享技能仓库只作分发镜像，修改回到主仓库。

仅维护一个 cohub 功能入口，英文和中文完整分发。App Developer 位于各包 references/app-developer，不得新增独立 SKILL.md。插件不得再维护 cohub-cards 创作 Skill；打包从通用 Skill 完整复制，对同一版本核对文件内容。更新检查器唯一作者源为 scripts/update-check.mjs；执行 node scripts/sync-checker.mjs 同步发行副本，--check 检查漂移。双语能力表保留可读描述，测试核对来源与路由一致，不模板化全部 Markdown。

两种语言 version.json 和 SKILL.md metadata.version 同步；metadata.language 与 version.json.language 一致。Skill 与插件独立编号；插件 manifest 与 package.json 的版本必须一致。不能把插件版本写成 Skill 版本，也不为仅插件变化强行递增 Skill。2.0.0 是此前安装结构变更正式版。正式 versions.json 不跟随候选版本递增，新 Skill 发布成功前保留既有正式指针。

## 两种安装包与重复入口

独立 Skill 的原仓库地址、两种语言路径、`cohub-v<version>` 标签、`versions.json` 地址与旧检查器继续有效；安装只取所选语言完整目录，不需要 plugin/、插件 Node.js 24 要求或 npm 依赖。

完整插件由根 `bash scripts/install.sh --language en|zh-CN` 安装，支持 `--skill-mode auto|bundled|external`、`--skill-path <path>` 与只检查的 `--check`。需要 Node.js 24+、npm、Git、Codex CLI、Cohub CLI。Codex CLI 也支持插件；卡片是否可见取决于宿主，不能称插件仅适合桌面。

- auto：发现同版本、同语言、文件内容一致的用户级独立 Skill 时用 external；只允许符合规范的 Init 清理差异；没有独立入口则用 bundled。项目内单独的 Skill 不能抑制用户级插件入口，不当作 external 复用来源。
- bundled：注册 `skills/cohub`。external：完整包仍携带相同 Skill 于未注册的 `bundled-skills/cohub`，注册的 `skills` 目录为空，保留原独立入口。
- 旧版、定制、缺字段、坏文件必须明确停止。不能覆盖文件、修改全局禁用配置、清空现场或把错误当作未安装。其他环境仍使用的 Skill 保留。
- 对外统一显示 Cohub；内部 `cohub-cards@cohub-cards-local` 标识不变，确保旧插件作为同一安装升级。
- 每次在全新的 `plugin/.packages/<id>` 打包，不覆盖旧 release。保留 Codex 仍引用的来源目录；不要清理活动包来“消除重复”。
- 插件缓存内的 Skill 随所属插件一起升级，不运行独立安装覆盖缓存。external Skill 升级后也须重新核对与插件携带版本的一致性。

## 构建与验证

独立 Skill：运行 `node --test tests/*.test.mjs`、`node scripts/sync-checker.mjs --check`、`node scripts/sync-explore.mjs --check`、`node scripts/build-explore.mjs --check`，检查双语完整包格式、引用自包含和旧版更新地址。

插件：在 `plugin/` 安装开发依赖后运行 `npm test` 和 `npm run build`。按两种语言和 bundled/external 两种模式分别调用 `node plugin/scripts/package.mjs --output <全新目录> --language <en或zh-CN> --skill-mode <bundled或external>`；核对包内 Skill 与来源内容一致、插件注册正确、依赖未进入独立 Skill、重复路径与定制内容会明确报错。不要在检查时真实生成、上传参考或发布作品。

验证安装前 `--check` 没有改写 Skill 或宿主配置；安装后分别验证 Skill 入口数与插件工具可用性。可视卡片另在支持的实际宿主验证，不能用工具注册或模拟测试代替。对语言切换、已清理 Init、旧版本、定制、损坏元数据、符号链接重复与旧插件升级路径保留回归覆盖。最后运行 `git diff --check`。实际行为验收另记录，结构通过不等于 Agent 行为通过。

## 正式发布顺序

1. 完成上方两个安装包的构建与验证，保留实际检查记录。Release notes 明确双包版本、语言、交互限制和迁移方式，不能把未做的实机或付费验证写成通过。
2. 取得该次提交、push 和 release 的明确授权。Skill 发行标签按包内版本生成 `cohub-v<version>`；仅插件发行可用 `cohub-plugin-v<version>`，无需强行递增 Skill 版本。联合发行在 Release notes 写明两包版本与固定来源。不照抄历史版本号，不移动已有标签。
3. 固定候选 commit，完成检查后在主仓库创建对应标签和非草稿、非预发布 GitHub Release，包含两种完整语言 Skill 与插件安装说明，记录 Skill/插件各自版本及包内关联。确认 tag 指向该 commit，Release 真实可读且已发布。正式插件安装从这一已验证 tag 与提交获取，不从可变 main 安装。
4. 仅在上述步骤成功且 Skill 版本变化时更新 versions.json 的 cohub 条目：version、released:true、tag、commit 和双语 notes。仅插件发行保留 Skill 正式指针，不能把 `cohub-plugin-v<version>` 写进 Skill 条目。用 gh release view <tag> --json tagName,isDraft,isPrerelease,publishedAt 及 git ls-remote --tags origin 核实；失败则保留上一个正式指针。推送指针仍须在该次授权内。
5. 读取公开版本清单确认 Skill 指针正确（仅插件发行时保持原值），然后才在旧 `cohub-plugin` 仓库发布升级桥接。桥接固定主仓库本次适用的正式 tag **及 SHA**，校验二者一致，保留用户原来的 `git pull` 后 `bash scripts/install.sh` 命令。桥接失败不能退回执行 main 或其他未核实代码；禁止先推桥再补主仓库 Release。
6. 核实旧安装路径能取得上述正式版，再更新 README 候选状态及升级说明。main 包版本与正式指针不要求相等；不要在主入口上写“已发布”直到发布真正完成。全过程保留旧标签、旧正式入口、作品与草稿，不自动升级用户本机安装。

保留 cohub-app-developer 旧正式条目供旧安装检查。统一版发布前不诱导升级到候选版；发布后可在旧条目 notes 提示迁移，但旧检查器只在版本增长时通知，不能虚造一个不存在的独立发行来强推迁移。迁移告知主要通过 README 和 Release notes。

历史核对记录：cohub-v2.2.1 是非草稿、非预发布 Release，2026-09-30 发布，tag 指向 0902e619628af513d165a386548003e750ce2b9f；旧 cohub-app-developer-v1.0.0 保留原标签与提交。当前正式版本以公开 versions.json 和实际 Release 为准。先完成 Release 再推送正式指针，历史标签不移动。
