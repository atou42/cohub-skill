# 费用与恢复

只在计费拦截、充值问题或选定的付费 App 工作流中读取，不在每次能力咨询或静态发布前检查余额。下述 CLI 行为核对于 8.4.1；以当前返回字段及本机帮助为准，不编造余额命令、价格或门槛。

## 分清拦截原因和谁付费

检查退出码与实际响应，使用 `--json` 时也读取 stderr。保留任务／操作 ID 和原始错误；HTTP 402 本身不等于余额不足。

| 依据 | 解释与下一步 |
| --- | --- |
| `billing_credit_limit_exceeded`，且 `billing.conversion.reason` 是余额原因 | 说明实际余额门槛，例如最低余额或负余额上限。只报告服务端提供的金额，不虚构统一门槛。 |
| `feature_not_entitled`，或 conversion reason 为 `feature_not_entitled` | 说明缺少的套餐／功能权益；充值普通余额未必能解除套餐限制。 |
| 成功响应中 `billing.status: "allowed_with_debt"` | 请求获准执行但有提醒；保留结果，不当成失败或重新生成。 |
| App commerce 消费返回 `status: "insufficient"` | 访客缺少该 App 的 Space 积分；解释对应商品，不默认引导充值平台余额。 |
| 计费字段缺失、无效，或其他错误 | 保留原错误并排查对应故障，不把登录、scope、模型策略或网络错误说成需要充值。 |

从实际调用确认执行身份与成本承担者。作者出钱的 Action、访客的平台余额、访客的 App 商业积分是不同对象。作者余额耗尽时，不要求访客充值自己的平台余额来修复；不擅自更换付费账号、执行身份或 Space 绕过拦截。

## 本地 Agent 与 CLI

CLI 8.4.1 对带结构化计费信息的 402 显示服务端标题、说明及账户设置提示；`--json` 则把响应体写入 stderr 并以非零退出。两条路径都不会自动打开浏览器。Agent 应简短说明受影响的步骤、付费主体、原因和下一步，不把整段原始 JSON 当成面向用户的完整答复。

提供已核实的计费链接，或说明从账户设置进入计费。返回的 `billing.conversion.primaryAction.href` 只是候选地址：核对其属于官方服务或当前部署，相对链接基于已确认的官方 origin 解析。不编造充值 URL，不因为链接出现在错误中就信任无关地址，也不在链接中暴露令牌。没有核实到直达入口时明确说明，给账户设置操作位置，不猜路径。

只有用户选择该动作或已明确要求打开时，才通过宿主支持的浏览器方式打开计费页。打开页面不等于允许选择商品、创建订单、付款或开启自动充值。不重复弹标签页，也不在本地聊天宿主中另造付款弹窗。

## 网页与已发布 App

Cohub 工作台的计费 UI 区分软提醒和硬拦截：前者使用可关闭提醒条，后者显示充值／升级面板。面板出现不等于支付成功；不能承诺每个已发布 App 或独立 SDK 使用者都会自动获得这套工作台行为。

付费 App 应保留输入和已完成结果，给出适合的、由用户触发的计费或购买入口。平台余额与 App 积分分开处理。选用 App 商品时，在用户购买动作中调用 `client.app.commerce.purchase({ productKey })`，不在页面初始化或错误重试时自动调用。使用实际配置的商品并核对当前[App 开发文档](https://cohub.live/zh/docs/developers/apps)；购买商业化商品不是通用的平台充值操作。

## 恢复时避免重复费用

- 打开计费页或从 checkout 返回都不是付款凭证。App 商业化需查询 `getCheckoutState()` / `getOrder()`，并刷新权威权益。平台计费使用已授权、有文档依据的余额／权益查询或官方确认；无法观察时如实说明，不宣称限制已经解除。
- 有原任务 ID 时先查原任务。排队／运行中的任务继续沿用 ID；已完成的任务复用结果；下载失败只重试下载。提交状态不明不能成为重发付费请求的理由。
- 恢复后继续原任务及原授权范围。新增费用或扩大范围须先确认；同一个商业化操作重试复用原幂等键，不为绕过错误重新生成扣费 ID。
- 用户取消或计费仍受限时，只暂停受影响的付费步骤。保留输入、结果和错误证据；无关的本地工作或已授权静态发布可以继续。
