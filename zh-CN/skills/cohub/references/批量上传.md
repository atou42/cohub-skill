# 大量小文件上传

仅在需要把大量零散文件传入 Space 工作区时读取。逐文件上传耗时明显时，优先将所需目录打包为 ZIP，上传单个包，再在目标工作区解压；文件已压缩时，主要收益是减少上传请求，不保证体积显著缩小。

## 默认切换标准

按排除无关文件后、本次实际需要传输的文件数计数，包含所需隐藏文件，不计目录：

- 少于 100 个文件：默认直接上传。
- 100 个文件及以上：优先打包 ZIP，上传后解压；仍需满足下方权限、工具及容量条件。
- 不足 100 个，但直接上传已明显缓慢或频繁限流：可以提前打包；先确认已有上传状态，避免覆盖或重复传输。

100 是便于执行的起始标准，不是实测最优值，也不是平台限制。大文件或超出单包限制时按实际传输条件处理，不能仅凭数量强行打包。

## 上传与核对

- 先确认用户目标 Space、上传目录和解压目录，以及可执行远端命令。不能把只读参考 Space 当目的地。无执行权限或无解压工具时说明限制，不把上传成功当解压完成。
- 打包前排除 `.git`、依赖目录、缓存、凭据和任务不需要的文件；保留所需隐藏文件、目录结构及资源，检查压缩包内的相对路径。检查目标大小限制与可用空间，解压需要额外空间。
- 先查当前 `spaces files upload --help` 和 `run --help`。上传到独立临时目录，避免覆盖已有同名包。例如（替换已核实的目标和路径）：
  ```sh
  cohub -s <目标SpaceID> spaces files upload ./bundle.zip --dir <独立临时目录> --json
  ```
- 确認上传返回的实际路径与完整性，再使用目标环境已有的解压工具，通过 `cohub -s <目标SpaceID> run --command '<解压命令>'` 解压到新的目录。检查包内条目不会通过绝对路径、`..` 或符号链接写出目标目录；有冲突时不强制覆盖。需要保留执行权限或符号链接时，先确认打包和解压方式能保留，不默认 ZIP 完整保真。
- 解压后核对文件清单、数量和关键文件内容；完整性要求高时对比校验值。确认入口和相对资源可用，再按原任务使用文件。失败保留压缩包与已知状态，从失败步骤继续，不反复全量上传；清理仅限确认成功且不再需要的本次临时文件。

**直接发布本地网页仍用 `apps publish --source local --dir`。** 不为使用此优化强行改成“先传工作区再发布”，也不把 ZIP 当成可直接运行的网页；工作区解压后的目录还需按正常发布流程处理。
