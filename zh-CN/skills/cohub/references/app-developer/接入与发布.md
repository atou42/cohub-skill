# 接入与发布

## 选择承载方式

尊重已有成果，只解释会影响交付的选择：

| 已有成果或约束 | 优先考虑 |
|---|---|
| 独立 HTML | file App；有相对依赖时确认全部随产物交付，必要时改用 directory |
| 静态站或前端构建产物 | 含 `index.html` 的 directory App，沿用原项目构建 |
| 需要持久在线服务 | 判断已有后端能否保留；需要 Cohub Sandbox 服务时才考虑 port App |
| 文档、媒体或 Board | 当前 App guide 的原生文件/Board 预览，不为发布强行包装成网站 |
| 明确计划，尚未实现 | 沿用用户本地开发流程，只在涉及 Cohub 时接入对应模块 |

file/directory/port 是承载类型，窗口/overlay/嵌入是展示方式，不混为一组选项。不要默认把已有网页改成悬浮层。
port 指 Cohub Sandbox 支持的公开端口，不是本机 localhost，也不承诺进程永远在线。静态发布不能自动承载 SSR、数据库或本地后端。

## 本地发布

1. 使用原项目 build/test，检查输出目录，排除 `.env`、凭据、开发文件和不该公开的数据。不要把仓库根目录当 dist。
2. 用 `cohub apps publish --help` 核对参数。明确目标账号、Space、slug、可见性及是否更新已有 App；不覆盖无关同名 App。未指定目标时先查明 CLI 实际默认目标，不把参考 Space 当默认值。
3. 只在发布范围已授权时执行。以下为模板，替换已核实的目标；`public` 仅在用户选择公开时使用：

```sh
cohub -s <target-space-id> apps publish <slug> --source local --file ./index.html --visibility public --json
cohub -s <target-space-id> apps publish <slug> --source local --dir ./dist --visibility public --json
```

静态 App 通常不需要 `--app-scope`。本地直接发布无需先将项目上传到 Space 工作区。
发布 SDK 的 `targetRef` 与 CLI `--source local` 不是同一种本地路径接口。

4. 读取返回的 App ID、URL 和状态；用 `cohub apps get --help` 后查询确认。不要手拼成功链接，不用 CDN 静态地址冒充 App 入口。
5. 更新时区分修改源文件、修改设置、发布新版本。原始源码改了不代表线上版本变了。本地更新重新发布本地构建产物，不能对旧 workspace target 盲跑 `publish-version`。

## 验证

- 打开返回的 App 链接，检查关键交互、相对资源、移动端布局和路由；页面不能只是 HTTP 200 的错误外壳。
- 对 SDK 接入，在真实 App runtime 中验证。普通 localhost/file 预览不足以证明授权、生成或 commerce 可用；没有发布授权则报告这部分尚不能验证。
- 如涉及访客，检查约定的匿名或其他登录用户路径。不能用作者会话冒充客态，也不使用未获授权的其他账号。
- 返回链接、此次发布的范围及可复用的更新命令。部署失败保留错误和远端状态，不为重试删除 App 或另建 Space。

更新已有 App 前，读取当前 App 身份、目标和可见性；保留原可见性，除非用户明确要求更改。不能因发布示例使用 public 而扩大访问范围。
