# 发布本地产物

## 确定产物与目标

- 单个 HTML 用 `--file`；包含 `index.html` 的目录站点用 `--dir`。需要构建时读取项目配置，沿用已有构建命令；不要假设输出一定叫 `dist`。
- 发布构建输出，不发布整个源码目录、`.git`、依赖目录或开发配置。检查引用的图片、字体、脚本、样式确实包含在发布范围内，避免本机绝对路径和仅本机可用的地址。
- 检查秘密、内部链接和未脱敏内容。发现问题先指出具体文件，不擅自清理用户源码。
- 沿用用户指定或已有 slug；首次可选简短、可读的项目名，不生成随机 UUID。用 `cohub apps ls --json` 检查目标 Space 的同名 App；不确定是否属于本次更新时先确认，不自动覆盖。
- 用户明确要求公开发布即可执行；只说预览、测试或生成并不代表同意公开。要求 Space 内可见时显式加 `--visibility space`；新建公开 App 时显式加 `--visibility public`。更新先读取 `cohub apps get <appId> --json`，保留已有可见性，除非用户明确要求更改。

## 发布与更新

下面 `<slug>`、路径和可见性均替换为实际值。用户指定 Space 时，在 `cohub` 后加 `-s <spaceId>`。

```bash
cohub apps publish <slug> --source local --file ./index.html --visibility public --json
cohub apps publish <slug> --source local --dir ./dist --visibility public --json
```

本地流程始终显式传 `--source local`，不要把本机路径交给 workspace 来源，也不需要先上传到 Space 工作区。`--file` 和 `--dir` 二选一；这一流程不发布本机开发服务器端口。

更新时重新构建，再用同一个 Space、slug 和新的本地产物执行 `apps publish`。`apps publish-version` 不代表重新上传本机文件，不拿它替代这一步。对于依赖后端、数据库或环境变量的应用，静态目录发布不等于完整部署，需报告缺失运行条件。

## 检查实际结果

1. 检查退出状态和 JSON，记录实际 App ID 与返回 URL，不从 slug 猜链接。若只拿到任务 ID，按当前帮助查询该任务，不能宣称已发布。
2. 打开返回 URL，确认不是错误页、意外登录墙或空白页，关键图片、脚本与样式加载成功。按用户指定的可见范围验证；不要为方便检查改成公开。
3. 更新已有 App 时确认是同一个对象、链接不变、内容已更新。CDN 延迟或浏览器不可用时说明尚未确认，不能用命令成功替代可视验证。

发布失败先查原任务或 App 状态，避免重复创建。身份缺少 username 或 Space slug 时，解释所需公开身份并让用户给定或确认；不擅自修改个人资料。

完成后返回可点击链接，必要时补一句发布了哪个产物。不要把日志或 URL 前缀当成交付链接。
